SchedulerFactory

final readonly class SchedulerFactory
{
    public const DRIVER_LARAVEL = 'laravel';

    public function __construct(
        private MutexInterface $mutex,
        private LoggerInterface $logger,
        private ClockInterface $clock,
    ) {}

    public function create(string $driver): SchedulerInterface
    {
        $scheduler = match ($driver) {
            self::DRIVER_LARAVEL => new LaravelScheduler($this->clock, $this->logger),
            default => throw new InvalidArgumentException(sprintf('Unknown scheduler driver "%s".', $driver)),
        };

        return new LockingScheduler($scheduler, $this->mutex, $this->logger);
    }
}

Nový scheduler = jedna nová větev v match. Kód aplikace se nemění.

LockingScheduler a LockedJob

final readonly class LockingScheduler implements SchedulerInterface
{
    public function add(ScheduledJob $job): void
    {
        $this->scheduler->add($job->withoutOverlapping ? $job->withJob($this->lock($job)) : $job);
    }
    // runDue() jen deleguje; zámek má klíč "scheduler:{name}"
}

final readonly class LockedJob implements JobInterface
{
    public function run(): void
    {
        $lock = $this->mutex->acquire($this->lockKey, $this->lockTtlSeconds);
        if ($lock === null) {
            $this->logger->info('Scheduled job skipped, previous run still holds the lock', …);
            return;
        }
        try {
            $this->job->run();
        } finally {
            $this->mutex->release($lock);
        }
    }
}

LaravelScheduler

Joby spouští přes eventy Laravel Scheduleru, ale bez Laravel aplikace. Každý job je CallbackEvent. runDue() nejdřív vybere eventy na řadě a pak je spustí, stejně jako artisan schedule:run. Co jsme ve zdrojácích Laravelu 12 ověřili:

final class LaravelScheduler implements SchedulerInterface
{
    public function __construct(
        private readonly LoggerInterface $logger,
        private readonly LaravelRuntime $runtime = new LaravelRuntime(),
    ) {}

    public function add(ScheduledJob $job): void
    {
        // cron-expression přijímá jen název timezone, ne DateTimeZone
        $event = new CallbackEvent(new DisabledEventMutex(), [$job->job, 'run'], [], $job->timezone?->getName());
        $event->cron($job->cron)->name($job->name)->nextRunDate();
        // nevalidní i nemožný výraz (0 0 30 2 *) → InvalidArgumentException
    }

    public function runDue(): void
    {
        // nejdřív výběr, pak běh: dlouhý job neposune vyhodnocení dalších jobů do jiné minuty
        foreach ($this->dueEvents() as $name => $event) {
            $this->runEvent($name, $event);     // $event->run($this->runtime), výjimku zaloguje
        }
    }

    private function dueEvents(): array
    {
        return array_filter($this->events,
            fn (CallbackEvent $event) => $event->isDue($this->runtime) && $event->filtersPass($this->runtime));
    }
}

/** Náhrada Laravel aplikace pro $app: kontejner + kontroly z Event::isDue() */
final class LaravelRuntime extends Illuminate\Container\Container
{
    public function isDownForMaintenance(): bool { return false; }
    public function environment(): string;
}

DisabledEventMutex implements EventMutex splní požadavek konstruktoru CallbackEvent. Laravel mutex se volá jen při withoutOverlapping(), které nezapínáme, takže je to jen pojistka: kdyby se ho něco pokusilo použít, vyhodí LogicException. Test testNeverUsesLaravelMutex to ověřuje.

Proč nepoužíváme zamykání Laravelu přes vlastní bridge? Šlo by to přes rozhraní EventMutex a SchedulingMutex. Zamykání by se tím ale přesunulo do adaptéru a crunz by potřeboval jiný bridge (symfony/lock). Stejný ScheduledJob by se pak mohl chovat jinak podle zvolené knihovny. Společný LockingScheduler drží chování stejné.

Čas bere Laravel z Carbonu (Date::now()). Testy ho nastavují přes Carbon::setTestNow(). SchedulerFactory si přesto drží ClockInterface pro implementace, které vyhodnocují cron pro zadaný čas (crunz).

RedisMutex

  • acquire: SET mutex:{key} {token} NX PX {ttl}, kde token je bin2hex(random_bytes(16))
  • release: Lua skript if GET == token then DEL, takže nikdy nesmaže cizí zámek
  • chyby: RedisException se převede na MutexException a job se nespustí

Proč ne Laravel mutex

Laravel 12 CacheEventMutex (withoutOverlapping()) u cache úložišť s podporou zámků (Redis, databáze) vytvoří skutečný zámek s náhodným vlastníkem. Jinde použije Cache::add(). Problém je v uvolnění: forget() si vytvoří nový lock objekt a zavolá forceRelease(), takže vlastníka nikdy nekontroluje.
